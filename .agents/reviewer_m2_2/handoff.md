### 1.2 `JarvisApp.process_text_command()` Integration
Direct inspection of `jarvis/core/app.py` (lines 516–591) confirms the execution pipeline:
- Strips and validates input text, safely returning `{"success": False, "error": "Empty command"}` on empty strings.
- Calls `self.llm_router.parse_intent(clean_text)` inside an isolated `try...except` block.
- Correctly passes `intent_result.parameters` as payload to `self.dispatcher.dispatch_action()`.
- Implements cascading response text extraction:
  1. Dynamic message in `action_result.data["message"]` (e.g. live CPU/RAM metrics from `HardwareReporter`).
  2. Generic LLM response reply (`parameters["reply"]`).
  3. `intent_result.response_text` generated by router.
  4. Contextual fallback via `llm_router.get_natural_response()`.
  5. Default fallback `"Tôi chưa hiểu lệnh này, vui lòng thử cách khác"`.
- Vocalizes the resolved `response_text` via `self.tts_manager.speak(response_text, wait=False)`.
- Updates System Tray status to `TrayStatus.ACTIVE` and broadcasts real-time telemetry event to `DashboardServer`.

## 3. Caveats & Non-Blocking Findings

### Finding 1 (Minor / Interface Polish): `parameters` vs `params` attribute alias
- **Observation**: `PROJECT.md` specifies `IntentResult.params`, whereas `IntentResult` dataclass field is named `parameters`.
- **Impact**: Low. Internal modules (`JarvisApp`, `LLMIntentRouter`) consistently use `intent.parameters`. However, external code expecting `intent.params` would encounter an `AttributeError`.
- **Recommendation**: Add a property alias `@property def params(self) -> Dict[str, Any]: return self.parameters` on `IntentResult`.

### Finding 2 (Adversarial / Safety Control): Pre-execution confirmation interception
- **Observation**: While `IntentResult` sets `requires_confirmation=True` and `danger_level="CRITICAL"` for power actions (shutdown/restart), `JarvisApp.process_text_command()` currently dispatches to `dispatcher.dispatch_action()` directly upon intent resolution.
- **Impact**: Medium (future safety). If a destructive power plugin is registered in later milestones, it would execute before voice confirmation is gathered from the user.
- **Recommendation**: In M3/M4 voice loop workflows, add an explicit confirmation check in `JarvisApp` before dispatching actions when `requires_confirmation` is true.

### Finding 3 (Exception Boundary): Fast-path Tier 1 error isolation
- **Observation**: In `LLMIntentRouter.parse_intent()`, Tier 1 regex rule evaluation is executed prior to the `try...except` block enclosing Tier 2.
- **Impact**: Very Low. `JarvisApp` already catches any outer exception from `parse_intent()`, but wrapping Tier 1 internally ensures cleaner fallback to Tier 3 directly within the router.
