# JARVIS Security Architecture & Threat Model

This document specifies the concrete security boundaries, threat mitigations, and execution isolation layers in the **JARVIS** platform (Windows 10/11 x64).

---

## 2. In-Process Python Defense-in-Depth

Untrusted code generated by AI agents runs within an isolated worker with:
1. **Two-Tier `sys.modules` Cache Poisoning**: Overwrites all pre-cached modules matching network, dynamic FFI, COM automation, and Windows reflection prefixes (`win32*`, `pywin*`, `comtypes`, `ctypes`, `socket`, `ssl`).
2. **`sys.meta_path[0]` Interceptor**: Preempts import lookups after cache clearing (`del sys.modules[...]`) and raises `PermissionError`.
3. **`sys.path` Sanitization**: Strips project workspace roots from `sys.path` to prevent importing internal modules (e.g. `jarvis.sandbox.security`).
4. **Output Stream Capping**: Limits `sys.stdout` to 1MB to prevent parent memory exhaustion attacks.

## 3. Restricted Token bootstrap-failure classification and CI compatibility mode

`spawn_low_integrity_process()` (`jarvis/sandbox/security.py`) distinguishes a genuine execution outcome (any exit code the user script itself produced, including a timeout) from a confirmed pre-user-code failure of the restricted-token backend (`RestrictedProcessBootstrapError`). **Production behavior on a confirmed pre-user-code failure is fail-closed**: `CodeInterpreterSandbox.execute_python()` refuses to run the script rather than silently retrying with weaker isolation.

**An NTSTATUS-shaped exit code such as `STATUS_DLL_INIT_FAILED = 0xC0000142` is, by itself, NOT proof that no user code ran.** A child can cross into the injected security preamble or even the user's own script and only later hit a native DLL load/init failure. The actual retry-safety boundary is a **readiness handshake**: the injected preamble writes an internal sentinel to stdout (through the already-installed 1MB output cap) as the very last step, after every guard has been installed and before the appended user code begins; being launched with `-u` makes this observable by the parent without buffering ambiguity. `strip_sandbox_ready_sentinel()` strips it from all output before it is surfaced or parsed. Only "known bootstrap-failure exit code AND the sentinel was never observed" is raised as `RestrictedProcessBootstrapError`; if the sentinel *was* observed, the child crossed the boundary and the outcome is treated as a genuine (if unusual) execution result — never retried.

`RestrictedProcessBootstrapError` additionally carries a `retry_safe` flag, `True` only where a failure is formally provable to have occurred before the child executed any instruction (a pre-`CreateProcessAsUserW` failure; Job Object assignment failing on a still-suspended child; `ResumeThread` itself failing, meaning the thread was never actually resumed). A failure discovered *after* the child was resumed (e.g. `WaitForSingleObject`/`GetExitCodeProcess` failing) cannot be proven pre-execution and is `retry_safe=False`. **Any generic, unclassified exception from the launcher is never retry-eligible, regardless of `retry_safe` or the compatibility flag.**

The restricted child is created with `CREATE_SUSPENDED` and is only assigned to the Job Object — then resumed — while still suspended, so it cannot execute a single instruction before the Job Object's `ActiveProcessLimit`/`JobMemoryLimit` bounds are confirmed in effect. Job Object assignment is fail-closed on both paths: on the primary Restricted Token path, a failed assignment terminates the still-suspended child without ever resuming it; on the compatibility `subprocess.Popen` path (which has no `CREATE_SUSPENDED` equivalent), a failed assignment kills the already-started process immediately rather than letting it continue unbounded — a documented, narrow, unavoidable race-window weakness specific to that opt-in path.

An explicit, narrow, opt-in environment switch — `JARVIS_SANDBOX_ALLOW_COMPAT_FALLBACK=1` — allows a confirmed `retry_safe=True` pre-user-code failure to fall back to the Job Object + scrubbed-environment `subprocess.Popen` path instead (no Low Integrity token). This exists because GitHub-hosted Windows Server CI runners have shown `STATUS_DLL_INIT_FAILED` under the Restricted Token launch path; `.github/workflows/ci.yml`'s Unit Tests job sets it for that reason only. It is never auto-detected from environment signals (e.g. `GITHUB_ACTIONS`), always logs a warning when active, and must never be enabled in production or in any release/package/security-validation workflow. Enabling it in CI validates that the Job-Object + scrubbed-environment path still functions on that runner — it does **not** validate Low Integrity Restricted Token isolation end-to-end there. As of this writing, CI has not yet been run with this change; that confirmation is still pending.
