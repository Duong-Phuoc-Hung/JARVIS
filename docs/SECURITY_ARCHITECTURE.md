# JARVIS Security Architecture & Threat Model

This document specifies the concrete security boundaries, threat mitigations, and execution isolation layers in the **JARVIS** platform (Windows 10/11 x64).

## 2. In-Process Python Defense-in-Depth

Untrusted code generated by AI agents runs within an isolated worker with:
1. **Two-Tier `sys.modules` Cache Poisoning**: Overwrites all pre-cached modules matching network, dynamic FFI, COM automation, and Windows reflection prefixes (`win32*`, `pywin*`, `comtypes`, `ctypes`, `socket`, `ssl`).
2. **`sys.meta_path[0]` Interceptor**: Preempts import lookups after cache clearing (`del sys.modules[...]`) and raises `PermissionError`.
3. **`sys.path` Sanitization**: Strips project workspace roots from `sys.path` to prevent importing internal modules (e.g. `jarvis.sandbox.security`).
4. **Output Stream Capping**: Limits `sys.stdout` to 1MB to prevent parent memory exhaustion attacks.

## 3. Restricted Token bootstrap-failure classification and CI compatibility mode

`spawn_low_integrity_process()` (`jarvis/sandbox/security.py`) distinguishes a genuine execution outcome (any exit code the user script itself produced, including a timeout) from a confirmed pre-user-code failure of the restricted-token backend (`RestrictedProcessBootstrapError`). **Production behavior on a confirmed pre-user-code failure is fail-closed**: `CodeInterpreterSandbox.execute_python()` refuses to run the script rather than silently retrying with weaker isolation.

**An NTSTATUS-shaped exit code such as `STATUS_DLL_INIT_FAILED = 0xC0000142` is, by itself, NOT proof that no user code ran.** A child can cross into the injected security preamble or even the user's own script and only later hit a native DLL load/init failure. The actual retry-safety boundary is a **readiness handshake**: the injected preamble writes an internal sentinel to stdout (through the already-installed 1MB output cap) as the very last step, after every guard has been installed and before the appended user code begins; being launched with `-u` makes this observable by the parent without buffering ambiguity. `strip_sandbox_ready_sentinel()` strips it from all output before it is surfaced or parsed. Only "known bootstrap-failure exit code AND the sentinel was never observed" is raised as `RestrictedProcessBootstrapError`; if the sentinel *was* observed, the child crossed the boundary and the outcome is treated as a genuine (if unusual) execution result — never retried.

`RestrictedProcessBootstrapError` additionally carries a `retry_safe` flag, `True` only where a failure is formally provable to have occurred before the child executed any instruction (a pre-`CreateProcessAsUserW` failure; Job Object assignment failing on a still-suspended child; `ResumeThread` itself failing, meaning the thread was never actually resumed). A failure discovered *after* the child was resumed (e.g. `WaitForSingleObject`/`GetExitCodeProcess` failing) cannot be proven pre-execution and is `retry_safe=False`. **Any generic, unclassified exception from the launcher is never retry-eligible, regardless of `retry_safe` or the compatibility flag.**

The restricted child is created with `CREATE_SUSPENDED` and is only assigned to the Job Object — then resumed — while still suspended, so it cannot execute a single instruction before the Job Object's `ActiveProcessLimit`/`JobMemoryLimit` bounds are confirmed in effect. Job Object assignment is fail-closed on both paths: on the primary Restricted Token path, a failed assignment terminates the still-suspended child without ever resuming it; on the compatibility `subprocess.Popen` path (which has no `CREATE_SUSPENDED` equivalent), a failed assignment kills the already-started process immediately rather than letting it continue unbounded — a documented, narrow, unavoidable race-window weakness specific to that opt-in path.

An explicit, narrow, opt-in environment switch — `JARVIS_SANDBOX_ALLOW_COMPAT_FALLBACK=1` — allows a confirmed `retry_safe=True` pre-user-code failure to fall back to the Job Object + scrubbed-environment `subprocess.Popen` path instead (no Low Integrity token). This exists because GitHub-hosted Windows Server CI runners have shown `STATUS_DLL_INIT_FAILED` under the Restricted Token launch path; `.github/workflows/ci.yml`'s Unit Tests job sets it for that reason only. It is never auto-detected from environment signals (e.g. `GITHUB_ACTIONS`), always logs a warning when active, and must never be enabled in production or in any release/package/security-validation workflow. Enabling it in CI validates that the Job-Object + scrubbed-environment path still functions on that runner — it does **not** validate Low Integrity Restricted Token isolation end-to-end there. As of this writing, CI has not yet been run with this change; that confirmation is still pending.

## 4. Self-healing truthfulness contract (`jarvis/healing/terminator.py`)

Added 2026-09-02, PR #31 (`fix/healing-truthfulness`, merge commit
`10d470237b0fe4bc295f02215b4606590d79d17e`). `AutonomousTerminator`/`HealingEngine` handle
autonomous process termination and reporting when the self-healing subsystem detects a hung
or resource-leaking application — a user-facing "success"/"failure" claim from this
subsystem is now backed by an explicit truthfulness contract, since an over-claimed success
here would mislead both the spoken/UI report and anything that later reasons about system
state from `HealingEngine.healing_log`:

- **Process termination success requires a confirmed backend result.** `.terminate()`/`.kill()`
  being called without raising an exception is never, by itself, treated as proof the
  process exited — `terminate_process()` only returns `True` after a confirmed outcome
  (`psutil.NoSuchProcess`, a successful `proc_obj.wait()`, or a nonzero Win32
  `TerminateProcess()` return value). A mocked/injected test backend is trusted only via an
  explicit `terminate_process()` callable's actual return value — never via the mere
  presence of a bookkeeping attribute such as `killed_pids`.
- **Failed or unconfirmed termination stays a reported failure** (`report["reason"] ==
  "TERMINATION_FAILED"`), including when the terminator raises an unexpected exception —
  the exception is caught locally and reported truthfully, never silently upgraded to
  success.
- **No fabricated recovery telemetry.** The previous synthetic RAM formula
  (`max(40.0, ram_percent - 25.0)`) is removed; nothing in this subsystem invents a
  post-recovery metric.
- **Reclaimed RAM requires an observed measurement.** `reclaimed_ram` is only ever the
  actual `ram_before - ram_after` delta (floored at 0.0, both measured via
  `_read_ram_percent()`), and is omitted from the report entirely — never defaulted to a
  placeholder — when RAM cannot be measured (no hardware provider, no `psutil`).
- **Unavailable telemetry remains unavailable.** RAM that cannot be measured is never
  silently reported as some default value; it is simply absent from the report.
- **User-facing success claims must correspond to the observed result.** "System
  overloaded" wording is only prepended when RAM was actually measured before termination
  and is at/above the configured `ram_threshold`; "success"/"đã xử lý" wording is only used
  after termination has been confirmed.

**PR #32 (`fix/wake-word-whisper-ci`, merge commit
`aaeeb53f834134bb4490147c238e82e863558caa`) is test-only** — it made
`tests/unit/test_wake_word_p0.py`'s Whisper-fallback assertion deterministic regardless of
whether `faster-whisper` happens to be installed on the machine running the suite. **It did
not change any production security architecture, isolation boundary, or wake-word runtime
behavior described elsewhere in this document** — do not cite it as a security-architecture
change.

## 5. Central dispatch truthfulness — action-outcome trust boundary (`jarvis/core/dispatcher.py`, `jarvis/core/app.py`)

Implemented and validated (not yet committed/merged as of this writing) on branch
`fix/dispatch-truthfulness`, 2026-09-03. `ActionDispatcher.dispatch_action()`/
`dispatch_action_async()` is the central choke point through which intent-routed commands,
gesture patterns, skills, and other consumers execute registered actions — it is a trust
boundary between an action handler's own outcome and everything downstream that reasons
about whether that action succeeded (the spoken/UI response, the interaction log, the
persistent memory episode log, and the `action.post_dispatch` event).

- **An explicit handler failure must never be upgraded into a dispatcher-reported success.**
  Previously, once a handler returned without raising an exception, the dispatcher
  unconditionally treated the outcome as `success=True` regardless of what the handler's
  return value actually signaled — silently discarding an `ActionResult(success=False, ...)`,
  a `{"success": False, ...}` dict, or a `{"status": "failed"/"error", ...}` dict. This is
  now normalized through a single shared function
  (`jarvis/core/dispatcher.py::_normalize_handler_outcome()`, used identically by both the
  sync and async dispatch paths) that recognizes only the established, evidence-audited
  failure/success contracts in this repository — see CLAUDE.md's durable
  "Dispatch truthfulness" invariant for the full contract and the return-convention audit
  behind it. Generic falsy data (`0`, `""`, `[]`, `{}`, `None`, a bare boolean `False`) is
  never treated as failure absent an established contract saying otherwise.
- **This is a truthfulness boundary, not a new isolation/authorization boundary.** It does
  not change, weaken, or bypass any existing security control: `SafetyGateInterceptor`'s
  destructive-action classification and confirmation-token binding (§8.3-equivalent in
  CLAUDE.md), RBAC/privilege interception, and `ACTION_NOT_FOUND` handling in
  `jarvis/core/dispatcher.py` are all untouched. `CONFIRMATION_REQUIRED` and every other
  `CONFIRMATION_*`/safety-gate failure reason remains a reported failure end-to-end (top-level
  application response, memory episode, interaction log) exactly as before — a gated
  high-risk action's real handler never executes without a valid confirmation token,
  independent of this change.
- **`jarvis/core/app.py`'s `process_text_command()` now derives its own truthfulness from
  `action_result.success`** instead of "no Python exception occurred," so a dispatcher-level
  safety/privilege/not-found failure and a handler-level explicit failure are both surfaced
  truthfully to the end user, to the persisted interaction log, and to the persisted memory
  episode — closing a path where a security-relevant failure (e.g. a rejected confirmation)
  could previously have been narrated back to the user, logged, and remembered as if it had
  succeeded.
- **The `hardware_status_query` compatibility alias (`jarvis/core/app.py::_register_core_actions()`)
  is a routing/registration compatibility fix, not a privilege or trust-boundary change.**
  It registers the same, already-`system_status`-registered handler
  (`self._handle_system_status`) under a second action name the router already intentionally
  emits — no new privilege level, no new RBAC path, no new safety-gate classification. It
  was this dispatch-truthfulness fix itself that correctly surfaced the pre-existing
  `ACTION_NOT_FOUND` this alias resolves (previously masked by the bug this document's §5
  otherwise describes).
